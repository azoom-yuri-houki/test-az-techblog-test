## 1. なぜ受託開発のPMOがAIのセキュリティに敏感になるのか？

自社プロダクト開発とは異なり、**受託開発には「顧客（クライアント）」が存在します。**
私たちが扱うコードや仕様書はすべてクライアントの資産であり、そこには機密情報や個人情報が多分に含まれています。

もし開発メンバーが「エラーを解決したいから」と、顧客のソースコードをそのまま公開設定のAIにインプットしてしまったらどうなるでしょうか。

- **ソースコード経由での機密情報漏洩**
- **顧客の知的財産権の侵害**
- **NDA（秘密保持契約）違反によるプロジェクト強制終了**

PMOとしては、メンバーの「開発効率を上げたい」という気持ちを尊重しつつも、こうした致命的なリスクを100%防がなければなりません。

## 2. 現場で実際に起きている「3つのAIセキュリティリスク」

実務の中で、特に注意深くチェックしているリスクは以下の3つです。

### ① プロンプト経由のデータ学習リスク
最も一般的なリスクです。無料版のAIツールや、設定を誤ったアカウントでプロンプトを入力すると、そのデータがAIの「再学習」に使用されてしまう可能性があります。
他社の開発の際、自社のコードの断片が「AIの回答」として出力されてしまうリスクがゼロではありません。

### ② 生成されたコードの脆弱性（ハルシネーション）
AIは非常に綺麗なコードを出力してくれますが、必ずしもセキュリティ的に安全とは限りません。
古いライブラリの非推奨関数を使っていたり、SQLインジェクションの脆弱性が含まれていたりすることがあります。AIが書いたコードをレビューなしでマージするのは、経験の浅いジュニア層のコードをノーチェックで本番環境にデプロイするのと同じくらい危険です。

### ③ シャドーAI（個人利用の検知困難さ）
会社やプロジェクトが「AI利用禁止」とルールを決めていても、メンバーが個人のスマホや私物PCのChatGPTを使って「ちょっとロジックだけ相談しよう」と使ってしまうケースです。これが最も管理が難しく、ガバナンスが効かない原因になります。

## 3. PMOとして実践している「現場のセキュリティ対策」

「危ないからAIを使うな」と全面禁止にするのは、現代の開発において現実的ではありません。開発スピードで競合に負けてしまうからです。
そこで私のプロジェクトでは、**「安全にAIを使うための仕組み化」**を進めています。

| 対策項目 | 具体的なアクション |
| :--- | :--- |
| **ツールの選定** | 商用利用可能で「データ学習なし（Opt-out）」が明記された Enterprise プランや、API経由での利用に限定する。 |
| **ルールの明確化** | 「顧客の仕様書・個人情報は絶対に入力しない」「関数単位のロジックのみ相談OK」など、プロンプトのガイドラインを策定。 |
| **コードレビューの徹底** | AIが生成したコードであることを明示させ、人間のシニアエンジニアが必ずセキュリティ観点でレビューを行う。 |

### 実際の運用Tips：ルールは「引き算」で作る
ガチガチのルールを作るとメンバーは守らなくなり、結果的にシャドーAIを誘発します。
「これはダメ」を10個並べるのではなく、**「法人プランのアカウントを全員に配るから、これ以外では絶対にやらないでね。これなら何を聞いても学習されないから安心だよ」**と、安全な道を用意してあげるのがPMOとしてのハックです。

## 4. エンジニア3年目でPMOをやってみて気づいたこと

エンジニアとしてコードを書いていた時期は「AIがあれば爆速で開発できる！」としか思っていませんでした。しかしPMOとして一歩引いた視点でプロジェクト全体、そして顧客との契約関係を見るようになってから、セキュリティファーストの重要性が身に染みてわかるようになりました。

AIは最高の相棒ですが、**「責任を取ってくれるわけではない」**という大前提を忘れてはいけません。

## まとめ：AI時代だからこそ、人間のガバナンスが価値を持つ

AIがどれだけ進化しても、受託開発における最終的な品質保証とセキュリティ担保の責任は人間にあります。

1. **学習されないクローズドなAI環境を会社が用意する**
2. **「入れていい情報」と「ダメな情報」の境界線をチームで握る**
3. **AI生成コードこそ、人間が厳しくレビューする**

この3点を徹底することで、セキュリティを守りながらAIの恩恵を最大限に受けることができると信じています。同じように現場のAI運用やセキュリティのルール作りに悩むPMOやマネージャーの方の参考になれば幸いです。
